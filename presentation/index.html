01. Problem

What happens in the first 72 hours

The 72h Window

Survival chances for people trapped in collapsed buildings or landslide debris fall sharply after 72 hours. Rescue teams have very little time to search large areas.

Time is the critical constraint
Network Failures

Cell towers go down, roads are blocked, and power cuts occur. Cloud-only dashboards and heavy online maps fail right when responders need them most.

Must work completely offline
Confusing Information

Responders receive duplicate calls, unverified rumors, and conflicting reports (for example, someone saying a house is empty while another says people are inside).

Bad data leads to wrong search priorities
02. Solution

What RescueGrid does

1. Clue Fusion & Conflict Detection

Extracts useful details from reports (headcounts, tapping sounds, battery status). Recognizes duplicate reports without inflating victim numbers, and highlights contradictions clearly.

2. Explainable Zone Prioritization

Divides the disaster area into searchable zones. Uses a clear formula (evidence, occupancy, urgency, time, access) and explains exactly why a zone got its score.

3. Safe Mission Dispatch

Recommends which team to send where based on skills (dogs for rubble, heavy cutters for concrete). Checks blocked roads so teams are never sent into hazards.

4. Works Without Internet

Saves all data in the browser (IndexedDB). Responders can add clues or check maps offline. Everything syncs back automatically when a connection is available.

04. Clue Processing

Handling duplicates and contradictions

Duplicate Detection

When multiple callers report the same victims, standard software counts them multiple times (turning 3 victims into 6 or 9).

Report 1: "3 people trapped under quarter 2 roof"
Report 2: "Family of 3 at quarter 2 needs help"
↳ Result: Merged as duplicate. Boosts confidence without double-counting people.
Contradiction Detection

If reports directly conflict, the system warns the coordinator instead of quietly overwriting older records.

Report A: "All residents evacuated to temple"
Report B: "4 people trapped in attic with low battery"
↳ Result: Flagged as Conflict. Coordinator alerted to physically verify before lowering priority.
05. Scoring Formula

Transparent zone prioritization

Every score is calculated using five clear, visible factors. No black-box machine learning.

Score = (0.30 × Evidence) + (0.25 × Occupancy) + (0.25 × Urgency) + (0.15 × Recency) - (0.05 × Access Penalty)
Evidence (30%)
Sensor signals, physical responder confirmation.
Occupancy (25%)
Headcounts, children, elderly, medical needs.
Urgency (25%)
Active hazards (mud creep, low phone battery).
Recency (15%)
Time since last contact. Does not assume death.
Access (-5%)
Road blockage penalty for heavy equipment.
Humanitarian rule: An area with zero reports is never marked "safe". It gets baseline vigilance. Coordinators can override any score with a reason

08. Offline Support

Built for zero-connectivity environments

1. Full Local Storage (IndexedDB)

All incident records, zones, clues, hazards, and missing persons are cached in the browser. Responders can view the map, read clues, and see rankings with no internet connection.

2. Offline Mutation Queue

When field workers submit a clue or register a missing person offline, it is stored in a local queue and appears immediately on their screen.

3. Automatic Sync & Conflict Checks

Once network returns, one click syncs all queued records. The server checks timestamps so older offline edits never overwrite newer command changes.

4. Offline Vector Grid Map Fallback

If OpenStreetMap tiles cannot load due to network loss, the system instantly renders an SVG vector grid with all 20 building footprints and road markers.
